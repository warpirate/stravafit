# StravaFit

An open-source, privacy-respecting alternative to Strava for recording, analysing and sharing runs, rides and other activities. *StravaFit* is a working name.

Repository: https://github.com/warpirate/stravafit

> **Status: Phase 0/1 in progress.** Research, design system and blueprint are done. The monorepo now has the shared Kotlin core (model, geo, polyline, metrics), the recording engine with a GPS test corpus, the file-format libraries (FIT, GPX/TCX, GeoJSON, route art), an Android app shell on sample data, and the Supabase backend v0 (schema, privacy rules, pgTAP tests). Recording does not reach the app yet, and there is no release you can install.

│   ├── fit/                  FIT encoder/decoder (written from the public protocol description)
│   ├── gpx-tcx/              GPX 1.1 and TCX v2 reader/writer
│   ├── geojson/              RFC 7946 reader/writer
│   └── route-art/            Route-art export: SVG posters, share cards, stories (samples/)
├── backend/                  Supabase: migrations, seed, pgTAP tests, verify-db.sh
├── infra/docker/             Self-host stack: Supabase compose, migrate job, PMTiles, Caddy
├── testdata/
│   ├── gps-corpus/           Synthetic GPS scenarios with goldens (generated by TrackGen)
│   └── files/                FIT/GPX/TCX/GeoJSON fixtures, goldens and a Python cross-check
├── design-system/            Tokens (tokens.json) and the reference Compose theme
├── docs/                     Research, specs, blueprint and ADRs (start at docs/README.md)
├── .github/                  CI (Gradle, Supabase, REUSE), issue and PR templates
├── LICENSES/, REUSE.toml     Per-path licensing (REUSE spec 3.3)

Android packages use the neutral placeholder `org.openactivity.*`; the libraries use `app.stravafit.lib.*`. Both will be renamed with the project (ADR-004).

## Build and test

Requirements: JDK 17, and the Android SDK (platform 35) for the Android modules. Point Gradle at the SDK with a `local.properties` file in the repo root (it is gitignored). Use one line: the first form is for Windows (escape `\` and `:`), the second for macOS and Linux.

```
sdk.dir=C\:\\Users\\you\\AppData\\Local\\Android\\Sdk
sdk.dir=/home/you/Android/Sdk
```

```bash
./gradlew build                                   # compile, lint and test every module
./gradlew :android:app:assembleGmsDebug           # Play build  -> android/app/build/outputs/apk/gms/debug/
./gradlew :android:app:assembleFossDebug          # F-Droid build (no Google services)
./gradlew :shared:metrics:test                    # one module's tests
./gradlew :android:core:recording:generateGpsCorpus   # regenerate the GPS corpus and goldens
./gradlew :lib:route-art:samples                  # re-render lib/route-art/samples/*.svg
```

If Gradle runs out of native memory on a smaller machine, add `--max-workers=2`.

Host-side Android tests (Robolectric and Roborazzi screenshots) run on the debug variants only. The committed screenshots are Windows reference renders and are not yet verified in CI.

## Run the backend locally

Docker is required for all three options. See [backend/README.md](backend/README.md) for the privacy model and the worker contract.

```bash
backend/scripts/verify-db.sh              # migrations + seed + pgTAP on a throwaway PostGIS container
cd backend && supabase start              # full local Supabase (Supabase CLI), then:
supabase db reset                         #   apply migrations and seed (3 demo users in Berlin)
supabase test db                          #   run the pgTAP tests
```

To self-host the full stack (Supabase, migrations, tiles, Caddy), follow [infra/docker/README.md](infra/docker/README.md).

## Contributing

Contributions are welcome. [CONTRIBUTING.md](CONTRIBUTING.md) covers setup, the module map, checklist IDs, commit style and DCO sign-off. In short:

1. Open an issue before starting large work so we can agree on scope.
2. Keep PRs small and link the checklist item they relate to.
3. **Clean-room rule:** do not copy Strava code, assets, icons, copy text or decompiled material. Describe observable behaviour in your own words and use our own design system.
4. Mark uncertain claims in docs as **(unverified)** and cite public sources where possible.
